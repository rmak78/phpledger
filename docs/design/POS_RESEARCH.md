# POS workflow research and baseline audit

**Status: research for the next design decision, 2026-09-14.** The user rejected the current POS/report experience. Current screenshots are baseline evidence, not an approved final design. Publication and broad implementation are on hold pending the lead's synthesis. A later explicitly authorized, narrow Enter-key posting safeguard and completion of missing local website screenshot assets are recorded below.

## Executive read

PHP Ledger needs a cashier workspace, not a catalog form. The current prototype can build a synthetic basket and calculate tender/change, but its large descriptions, quantity inputs and long guidance compete with the sale itself. Official Shopify, Square and Odoo workflows all give deliberate structure to item selection, payment and completion. That agreement supports a better starting pattern; it is not evidence that their interfaces are universally usable or that our proposed design has been tested. Retain the central posting/duplicate protections and rebuild the interaction around a persistent current sale, one-tap item entry and an explicit payment stage. Keep this first direction scoped to a general shop cash sale until industry, tax, inventory and device requirements are agreed.

Audience: an SME cashier/owner using a desktop or landscape tablet, with a usable mobile fallback. Horizon: the next POS design/build iteration. This is a bounded primary-source comparison plus a local UI audit, not customer-interview research, a market survey, hardware certification or regional tax guidance.

## Ranked problems and proposed moves

| Priority | Problem / user goal | Evidence and confidence | Proposed move |
|---|---|---|---|
| P1 | Complete a sale deliberately | All catalog/search/quantity fields share the checkout form. `pos.js` has no Enter-key guard; once cart/tender are valid, native implicit form submission may activate checkout from a search or quantity field. **High-confidence code risk, not triggered in this audit.** | Separate browsing/editing from final confirmation. Test Enter in every field against a synthetic disposable sale before release. No search, scanner terminator or quantity key should post a sale. |
| P1 | Keep current total and Pay reachable | Tablet/mobile geometry above; same two-item basket. **Directly observed**, prevalence outside this fixture unknown. | Use a persistent total/Pay action, independently scrolling catalog and basket, and a mobile basket sheet with sticky total. Keep keyboard focus visible when opening it. |
| P1 | Make quantity corrections quickly | Basket lines show quantity and Remove, while editable quantities are on catalog cards. **Observed and source-confirmed.** | Put quantity stepping and an explicit quantity editor on the basket line. One tile press adds one item; repeated presses increment predictably. Show immediate feedback and preserve focus. |
| P2 | Recognize products without reading a brochure | Three large desktop cards and only the top of the first mobile row fit in the baseline opening. **Observed.** | Compact tile: recognisable thumbnail when licensed/available, short name, price, optional SKU/variant. Move long descriptions into item detail. Use a consistent text fallback rather than oversized letter blocks. |
| P2 | Find known items at speed | Search currently filters name/SKU locally; no scanner handler or dedicated result-selection path is present. **Source-confirmed; hardware untested.** | Add a focused search workflow with clear no-result recovery. Design scanner input only after exact product/variant identifiers and HID device behavior are agreed. |
| P2 | Recover without redoing the sale | Server validation retains submitted data, but browser-side cart state has no persistence and no visible held-order control. **Source evidence; reload recovery not executed.** | Specify a bounded draft-cart lifecycle, confirm leaving a nonempty sale and show an honest uncertain-result recovery path. Hold/recall requires durable ownership and expiry, not decorative buttons. |
| P2 | Use controls accessibly | All six quantity fields have the same programmatic label, Quantity; navigation has a mobile inner scrollbar. **Observed DOM/capture.** | Include the product name in quantity labels, expose add/remove/total changes to assistive technology without excessive announcements, fix navigation reflow, and test keyboard/touch targets. |
| P2 | Understand status without constant technical noise | The opening viewport devotes considerable room to broad warnings and backend explanations. **Observed.** | Keep a concise persistent Sample/Cash-only status. Put detailed scope near Help and payment confirmation, while preserving any information needed to avoid a mistaken real payment or tax assumption. |

Frequency is not measured: this was one scripted synthetic journey at three widths. Agreement across vendor documentation supports the design pattern, not a claim about how often our users encounter a problem. No severity ranking implies an accounting defect was observed beyond the expressly identified interaction risk.

## Recommended next design: a focused register

Use a compact PHP Ledger shell with an unmistakable company/register context and a simple **Sell → Payment → Receipt** progression. On desktop/landscape tablet, place search and compact product/category shortcuts in the larger pane, with the current sale in a roughly 360–420px pane. Pin the total and **Pay [amount]** control within that pane. Let long product or cart lists scroll without moving the payment action off screen. On mobile, show a persistent basket count/total button that opens a dedicated basket view; do not place checkout after the full catalog.

The product tile should be one clear add action. Selecting a basket line opens its quantity controls; restricted future price overrides or discounts belong in a controlled action menu only when their server rules exist. Search/scan focus and Enter behavior must be explicit. A payment panel should show amount due, Cash, exact tender, appropriate configured denominations, custom amount and prominent change, followed by one deliberate confirmation. Do not hard-code USD note denominations as a universal country rule.

The completion screen should show Recorded, receipt number, total, tender and change, with Print receipt and Next sale as the primary next actions. Keep accounting trace links available to authorized users without forcing the cashier to review a journal. A print failure should leave the same saved receipt recoverable. Do not label browser acknowledgement as printer success or treat an uncertain network response as permission to start a duplicate sale.

Visually, the product should remain recognisably PHP Ledger: navy structure, restrained blue for the main action, readable Inter, clear prices and quiet separators. Usable density matters more than large decorative blocks. The next visual proposal should show the populated register, payment correction and completed receipt together, not only an attractive empty screen.

## Scope and acceptance before implementation

**Next design/build iteration:** compact register, basket quantity editing, persistent total/Pay, explicit cash payment stage, completion/reprint, keyboard focus and responsive checks. Preserve central posting, fixed-precision amounts, server prices, identity scoping and duplicate prevention. Prototype the interaction using existing cash-only semantics before broadening the product.

**Later backend milestones:** held orders, proper sales/returns history, cashier/register permissions, till opening/closing and reconciliation, real product/variant catalog, stock/COGS, invoice-based credit sales, customer balances, tax and receipt adapters, payment terminals, and any offline queue. These are dependencies, not UI controls to pretend are functional. Shopify's [offline checkout guidance](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/selling-offline/offline-checkout) illustrates that offline operation entails permission, reconciliation and data-loss considerations; a PHP Ledger offline claim needs its own durable design and tests.

Proposed acceptance targets, to agree before the next implementation:

- At 1366 × 768 and 1024 × 768, cashier can see current total and Pay without page scrolling during a normal basket edit.
- At 390 × 844, basket and total remain one action away while browsing; virtual keyboard does not hide the current action or error.
- One tile action adds one product. Cashier can increase/decrease a basket line without searching the catalog again.
- Enter in search, barcode and quantity paths never posts. Only explicit payment confirmation reaches the posting endpoint.
- A six-item sample sale, one quantity correction and cash change can be completed unassisted by at least four of five initial test participants; measure completion time before setting a speed claim.
- Server rejection retains the basket/tender and identifies the correction. Retry after an uncertain response resolves to one durable receipt and one journal.
- Keyboard order, focus return, product-specific labels, change announcements, 200% zoom, actual 80mm receipt output and the chosen scanner receive explicit checks. Screenshots alone do not prove them.

The first retail business type, primary device/scanner, receipt obligations and treatment of variants still need confirmation; the subsequently confirmed country order is recorded below. Restaurant modifiers/tables, pharmacy batches/expiry and distributor pack units should be separate validated workflows rather than modes added to this generic grid.

## Narrow safeguard and local asset completion

The [HTML implicit-submission rules](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#implicit-submission) establish that the first submit button is the form's default and that a disabled default prevents implicit submission. The POS form now has a hidden disabled default submitter; the visible **Record cash sale** button carries `checkout_intent=record_cash_sale`. JavaScript suppresses Enter in editing inputs, requires the actual checkout submitter and prevents repeated submits while keeping the named button in the posted data. The lead added the matching route rejection for missing or invalid intent. This is an interaction safeguard, not a substitute for authentication, CSRF or accounting validation.

Observed Chrome check in a newly created, isolated **POS Keyboard QA 2026-09-14** company (company 5): a valid notebook basket and USD 10 tender stayed on `/pos` after Enter in search, quantity and tender. Deliberately pressing Enter on **Record cash sale** created **POS-000015**, source 15 / journal 11, USD 4.50 total and USD 5.50 change. The original Core accounting sample was not changed. JavaScript syntax and PHP template lint passed. The separate HTTP workstream reports 21 passing checks, including missing/invalid intent with no accounting effect. Native JavaScript-disabled browser execution was not available through the supported testing capability; its default-button behavior is standards-backed and remains a runtime check for the next acceptance pass.

All five referenced owner/POS website images now exist as compressed derivatives of the actual local captures, with original PNGs retained. Intrinsic dimensions match the output files. Static markup/asset/anchor/CSS checks report zero errors; the conservative expanded file budget is **591,936 bytes**, including the first owner screen, POS screen and both lazy secondary photos; JavaScript is **7,259 bytes**. This is a local development baseline, not an accepted redesign or publication receipt.
